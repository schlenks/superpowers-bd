# Beads 0.49.4 → 1.3.0: implications for Superpowers-BD

**Reviewed:** 2026-09-22. **Installed CLI:** Homebrew `bd 1.3.0`. **Baseline:** the repository's February 2026 [v0.49.4 Dolt/concurrency analysis](IMPROVEMENTS-ARCHIVE.md#43-beads-v0494-concurrency-architecture-verified-feb-7-2026). This is a product and integration review, not a claim that every upstream change should be adopted.

**Historical snapshot:** Repository and CLI observations below refer to the
review date. Preserved on 2026-10-10 with local link validation; the upstream
review and isolated Beads probes were not repeated. The generated gate lock
is now ignored by the root `.gitignore`.

**Conclusion:** Beads has moved from a Dolt migration in progress to a stable embedded store with safer graph writes, epic-scoped work selection, and race-aware claims. The most immediate Superpowers-BD gains are correcting stale storage/sync guidance and replacing manual global-ready filtering. Atomic plan import and lease-based recovery are promising but need parity and liveness tests before becoming defaults. Follow-up [adoption experiments](BEADS-1.3.0-ADOPTION-EXPERIMENTS-2026-09-22.md) refine the scope and import recommendations below.

## Evidence and scope

- Read the tagged upstream [v1.3.0 changelog](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md) from the 0.49.5 entry through 1.3.0, including the 1.1 release candidates because 1.1.0 incorporates them. Cross-checked the [1.3.0 release notes](https://github.com/gastownhall/beads/releases/tag/v1.3.0), installed CLI help, and tagged [graph-plan schema](https://github.com/gastownhall/beads/blob/v1.3.0/cmd/bd/help_supplements/create_graph_plan.md).
- Compared those contracts with this repo's Beads skill, plan2beads, SDD, execution, recovery, setup, and session hooks. No production issue was used as a feature probe. An ignored, isolated `temp/beads-review-probe/` database supplied the graph, scoped-ready, atomic-claim, guarded-update, and heartbeat receipts below.
- The review stops at stable 1.3.0. A 1.3.1 release candidate existed on the review date, but is outside the requested range.

## Highest-value opportunities

### 1. Correct current Beads guidance and generated-file hygiene

The repository still says `bd sync` is deprecated/no-op in [AGENTS.md](../AGENTS.md), [the Beads sync reference](../skills/beads/references/sync-workflow.md), and [the session-end hook comment](../hooks/session-end.sh). That was true after 0.51.0; it is false in 1.3.0. The current `bd sync` is a bounded pull, conflict-check, blocked-state recompute, and push loop with distinct exit codes. It is an **explicit remote operation**, not a replacement for local auto-commit. Keep the current no-automatic-push policy; document `bd sync` as an available user-controlled federation action. It also requires consent before adopting a Git-origin-derived Dolt remote. [1.2.1 change](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L1949-L1983), [1.3.0 remote guard](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L134-L140).

The [Beads troubleshooting reference](../skills/beads/references/troubleshooting.md) is more than stale: it recommends daemon controls, `sync.branch`, and resolving JSONL conflicts with `git checkout --theirs`. Those belong to the removed architecture and the wholesale conflict choice conflicts with this repo's semantic reconciliation rule. Replace the page with current embedded-Dolt, worktree, backup, and conflict recovery guidance; do not execute its old commands.

The sync reference also calls `bd export` a disaster-recovery snapshot and implies `bd backup sync` always writes into `.beads/backup/`. A JSONL export captures issue content but not a full database/history/config backup; `bd backup sync` requires a configured destination. Fix those instructions before any automated upgrade or recovery advice. The current store is embedded, has auto-commit `on`, and has an `origin` Dolt remote; no remote sync was run during this review. [1.0.5 storage model](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L3486-L3504), [1.3.0 backup ordering](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L48-L91).

1.3.0's cooperative gate creates persistent `*.gate.lock` files. A zero-byte `.beads.gate.lock` is currently untracked at the repo root; upstream says `bd doctor --fix` adds the ignore pattern. Add the exact pattern through a reviewed `.gitignore` change, preserving the current working tree. The general `bd doctor` still does **not** run in embedded mode: only `--check=artifacts`, `conventions`, and `pollution` are supported, plus limited hook health. Do not make generic `bd doctor` a completion gate here. [Gate change](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L210-L228).

### 2. Use Beads' epic-scoped ready/blocked queries

SDD and executing-plans currently run global `bd ready`/`bd blocked`, then manually intersect results with an epic's children. `bd ready --parent <epic-id>` and `bd blocked --parent <epic-id>` now scope to that epic's **descendants** in Beads. The isolated fixture returned the ready child and two blocked siblings, and a follow-up nested fixture showed that `ready --parent` also returns a ready grandchild. If the workflow intends direct child tasks only, intersect the scoped result with `bd list --parent <epic-id>` or check each row's `parent`. Retain `bd show <epic-id>` as a relationship check. This reduces cross-epic dispatch risk and tool output without changing dispatch depth accidentally. [Current SDD routing](../skills/subagent-driven-development/dispatch-and-conflict.md), [current execution routing](../skills/executing-plans/references/epic-scoping-and-deadlock.md), [upstream ready-parent addition](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L4316).

For machine reads, `--brief --json` omits free-form text; fetch full task bodies with `bd show <id>` only for selected work. A snapshot of this repo's nine active issues was 10,148 bytes with `bd list --json` and 4,426 bytes with `--brief` (56% smaller). This is a local byte comparison, not a token or latency benchmark. `bd ready --brief` requires `--json` and cannot combine with `--claim`, so keep selection and claiming separate where file conflicts must be checked first. [Upstream brief contract](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L988-L1024).

### 3. Pilot atomic plan import, with a deliberate ID migration

The current [Claude plan2beads flow](../commands/plan2beads.md) creates an epic, then each child separately, then dependencies. A failure can leave a partial epic. In 1.3.0, `bd create --graph plan.json --dry-run --json` validates structure, and live `--graph` creates the nodes and edges transactionally. The tagged schema supports descriptions, acceptance, labels, estimates, parent relationships, and plan-local symbolic keys; output maps keys to minted IDs. An isolated four-node probe preserved those fields and dependencies, and ready/blocked matched the declared graph. [Tagged graph schema](https://github.com/gastownhall/beads/blob/v1.3.0/cmd/bd/help_supplements/create_graph_plan.md), [tagged implementation](https://github.com/gastownhall/beads/blob/v1.3.0/cmd/bd/graph_apply.go).

This is **not** a drop-in replacement. Graph children get flat IDs and do not inherit parent labels **when IDs and labels are omitted from their nodes**, while current plan2beads examples and downstream prompts use `epic.1`-style IDs. A follow-up fixture proved that explicit `id` values preserve dotted IDs in a single atomic graph create. The converter must allocate unique IDs and supply every child's labels. Dry-run validates graph structure but can pass a missing external dependency that live creation rejects; unknown fields warn rather than fail. Keep the present flow until a fixture-based pilot proves parity for Global Constraints, Interfaces, Review Focus, verification gates, labels, dependency direction, error rollback, and both Claude/Codex imports. [Graph limitations](https://github.com/gastownhall/beads/blob/v1.3.0/cmd/bd/help_supplements/create_graph_plan.md).

`bd create --file` also became all-or-nothing in the 1.2 development line, but the follow-up fixture showed that it rejects `--dry-run` and ignores a `### Parent` section. It cannot directly represent the current plan2beads hierarchy. `bd batch` is **not** a general plan importer: its create grammar lacks descriptions, parent relationships, acceptance criteria, and labels. Its `close` subcommand also does not enforce the same done-status close policy as `batch update`, so it should not replace SDD's evidence-gated close flow. [File semantics](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L2220-L2263), [batch semantics](https://github.com/gastownhall/beads/blob/v1.3.0/cmd/bd/batch.go).

### 4. Pilot leases and guarded claims for interrupted waves

The current SDD dispatch changes selected issues with `bd update <id> --status=in_progress`; checkpoint recovery unconditionally resets old in-progress tasks to open. That can steal work if a live agent or another session owns it. A `bd update <id> --claim` is atomic, records an assignee and a five-minute lease, and can be refreshed by `bd heartbeat`. `bd reclaim` only reopens expired leases after a grace period. `--if-assignee`/`--if-status` provide compare-and-set transitions with exit code 13 for a lost race. The isolated fixture showed scoped `bd ready --claim` setting `lease_expires_at`, a successful heartbeat, and a guarded reassignment refusing with exit 13 and no write. [Current recovery](../skills/subagent-driven-development/checkpoint-recovery.md), [upstream leases/CAS](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L3060-L3129).

Do **not** turn on automatic reclaim from prose alone. A five-minute lease expires during many implementation tasks unless a supervisor heartbeats. Each subagent needs a distinct, stable Beads actor; multiple agents sharing the same Git user are not sufficient ownership evidence. Reclaim must be scoped by exact issue IDs and assignee, and run on the replica that granted the lease. Checkpoint recovery must verify liveness before resetting an issue. Pilot this on an isolated epic with live, paused, crashed, and cross-replica cases before replacing the current recovery path. [Replica guard](https://github.com/gastownhall/beads/blob/v1.3.0/CHANGELOG.md#L1924-L1948).

## Recommended order

1. **Documentation and hygiene:** correct `bd sync`, backup/export, `bd preflight`, and embedded-doctor guidance; replace the obsolete troubleshooting page; add a gate-lock ignore pattern and a version/backup warning to the setup documentation. Keep remote sync explicitly user-controlled. This is the smallest concrete next change.
2. **Scoped reads:** use `bd ready --parent` and `bd blocked --parent` in SDD/executing-plans/plan2beads, with focused tests that include unrelated ready issues. Add `--brief --json` only where a parser consumes the listing, then fetch selected full bodies.
3. **Atomic import experiment:** characterize the current plan2beads output and failure behavior, then test `--graph` with explicit dotted IDs and labels against the same fixtures. `--file` does not carry the required hierarchy. Resolve collision-safe ID allocation before changing the default.
4. **Lease experiment:** assign distinct actors, heartbeat under long-running work, and test reclaim/checkpoint recovery on a dedicated fixture. Keep current recovery until no live claim can be reset.
5. **Optional observability:** enable the events journal only if a measured local monitoring use case needs it; keep durable reports in comments/history/checkpoints.

No production Beads schema, remote, sync policy, or workflow implementation was changed by this review.
